# 関連システムとの衝突 — th-system の見解（検討メモ）

**spec ではない。**2026-11-01 に th-system の実装管理担当（セッション `th-system-74`）から受けた見解の記録。
**th-system 側ユーザーの判断はまだ取っていない私見で、決定ではない。**
出典の節は、本システムの実装管理担当が th-system の原文（`main` `8884d9f`）で確かめた。
結論とユーザーに決めてもらうことは [conflicts.md](conflicts.md)、衝突の一覧の正は [Spec-open.md](spec/Spec-open.md) §1.1。

## 1. 地図（本システム `FK-S5`）

**読みは合っている。**前日の地図を必須にしている箇所は 3 つある。
- th-system `Spec-onsite.md` §1: 試験場内地図は前日に作り、1 枚だけ持つ。
- th-system `Spec-onsite.md` §4.0.3 と `Spec-modes.md` `SM-3.1.2-119`（2026-10-23）: 会場地図を持たない間は、盤前移動・待機場所への移動・呼び寄せを始めない・再開しない（拒否する）。
- 冒頭の注意 `CL-R-1`: 呼び寄せも地図が必須。

地図のない所を SLAM で走るときに妨げになるもの:

| # | th-system の決まり（出典） | 本システムの SLAM 走行とのぶつかり |
| --- | --- | --- |
| a | **経路が決まったあとは自動で別のルートを探さない。別のルートを探すのは試験員が「再検索」を押したときだけ**（`Spec-onsite.md` §6。2026-10-04。理由は、納品前の製品がある場所で人が予期しない道へ回り込ませないため） | 地図が育つたびに経路を引き直すのと正面からぶつかる。**本システムが出す「再計算の指示」も人の操作ではないので同じ** |
| b | **自己位置を見失ったら非常停止する**（`LOCALIZATION_LOST`。オドメトリと自己位置推定が並進 1.0 m／回転 0.5 rad 以上食い違ったとき。`Spec-safety.md` §3.5.0） | SLAM でループが閉じて地図の座標が飛ぶと、これが鳴る見込み。地図作成中にこの監視を外しているのは「自律で走らないから」で、自律で走りながら外すと安全網が無くなる |
| c | **走りながら地図を書き足す「地図更新 ON」は使えなくしてある**（`Spec-onsite.md` §4.0.1 段 B。2026-10-22。地図が動いて自己位置が飛ぶ恐れへの設計が決まっていないため）。地図更新 OFF の間は地図を凍結する（§4.0.2） | 本システムの SLAM 走行は、この未解決の問題の上に乗る |
| d | **走る前に、引いた経路を 0.55 m 角の機体の形で検査する**（`Spec-onsite.md` §6.1.1） | 地図のできていない所をどう扱うかが決まっていない。通れない扱いなら走れず、通れる扱いなら G1 の保証が弱まる |
| e | **ピンは地図の座標**（§4.0.1 で「地図がずれるとピンもずれる」を最も重いとしている） | 本システムの目的地は ss-system の配置図から出るので、th-system の地図の座標に載せる変換が要る（`FK-A6`） |

th-system にも「SLAM 自律」を候補に戻すかの未決 `O-d8` があるが、これは全域の地図を事前に作る前提で、未知の所を走る話ではない。

**前日の地図に寄せた方がよい理由（th の見解）**: a〜e がすべて消える。盤前移動の仕組み（会場地図・塞がれたときの待ち・到着の許容差・向き合わせ）をそのまま使える。
前日に地図を作るので、当日の自律測定の時点で地図はある。th に新しく要るのは「**ピン以外の座標（配置図から出した盤前の位置と向き）を行き先として受ける口**」くらい。

- th でできそうか: 前日の地図に寄せるならできる（既存の延長）。地図のない所を SLAM で走るのは、今の決まりのままではできない。
- ユーザーの判断: 要る（th-system の §6・§4.0.3 を変えるか、本システムの `FK-S5` をどちらに倒すか）。

## 2. 作業中ボタン（th-system `O-a6`）と「指示を受けるモード」（本システム `FK-U2`）

**置き換えはできそう。**th-system `Spec-onsite.md` §7.2 は、もともと「昇降・撮影側との結合設計が決まったら、作業中ボタンを正式な信号（到着通知／昇降完了／撮影完了／中断通知）に置き換える」と書いている。
ただし作業中ボタンは盤前に着いた状態（`AT_PANEL`）の中だけのもの。本システムのモードは盤から盤への移動まで含むので、**作業中ボタンの範囲を広げる形**になる。

モードの抜け方と、モード中の画面（th の私見）:

| 項目 | 見解 |
| --- | --- |
| 抜け方 | th の画面から**いつでも抜けられる**。測定が終わったら自動で抜けてもよい |
| 抜けた先 | 止まった状態（盤前か待機場所で待つ）。**抜けただけでは動き出さない** |
| 本システムが落ちた・通信が切れた | th は止まって待つ（`FK-X2`） |
| 非常停止・中断・一時停止 | SD-3 のとおり**常に効く・常に押せる** |
| 手動走行 | 人が触ったら本システムの指示より**人を優先**。ジョグで一時停止に落ち、手を離しても止まったまま（`SM-3.1.1-02`） |
| 行き先選び（ピン・呼び寄せ・待機場所） | 本システムの指示とぶつかるので、**モード中は拒否**（作業中と同じ扱い） |

**大きい論点は SD-8**（th-system `Spec.md` §5「モードの切替はすべて明示操作による。試験員が押していないのにロボットが動き出す経路を作らない」）。
th の当日の流れは「1 回の移動に人の操作 1 回」で、盤前に着いたら止まり、次の行き先は人が選ぶ（`SM-3.1.2-066`）。
自律測定は 1 回選ぶと、複数の盤・点と点のあいだを続けて動く。「本システムへ移るボタン＋盤を選ぶ」を、その後に続く移動すべての明示操作とみなすかは、SD-8 の読み方を変えることになる。
発進前に周りを確かめる仕組み（呼び寄せの退避待ち §5 に当たるもの）を自律の発進にも置くかも、一緒に決める必要がある。

- th でできそうか: できそう（盤前の状態と作業中ボタンの延長）。
- ユーザーの判断: 要る（SD-8 の扱い、モード中に th の画面で何ができるか）。

## 3. 申し送り（[Spec-open.md](spec/Spec-open.md) §1.2 の th-system の 4 行）

| 申し送り | 見解 |
| --- | --- |
| 目的地を受け、経路の計画・走行・停止は th | 目的地を受けること自体はぶつからない。**再計算の指示はぶつかる**（§1 a）。塞がれたら th は止まって待ち、別ルートを探すのは試験員が押したときだけ。本システムがその「押す」の代わりになってよいかはユーザーの判断 |
| 到着・状態を返す | ぶつからない。モード・状態・塞がれ・到着・フォルトは th が既に持っているので、出すだけ。`O-a6` の「到着通知」に当たる |
| 盤前でのその場旋回 | **条件つき。**盤前で待つ状態の速度上限は「停止」で、ジョグ中だけ極低速（th-system `Spec-modes.md` §6）。自律の旋回は今は到着時の向き合わせだけで、盤前で外から旋回の指示を受けるのは新しい振る舞い。**0.55 m 角の機体は旋回で角が大きく振れ、障害物の前でその場旋回してはならない**（`Spec-onsite.md` §6.3。障害物リミッタは前進は止めるが旋回は通す）。盤前で旋回するなら盤との距離を条件にする（本システム `FD-5` に直結）。**精度**: クローラはその場旋回でいちばん滑る。自己位置推定の補正の最大（37 cm／10.5°）はどちらもその場旋回中に出た（`Spec-safety.md` §3.5.0）。到着の許容差は ±0.12 m／±0.12 rad。5 点に要る精度（`FK-V4`）がこれより厳しいなら、旋回だけでは足りないかもしれない（th `O-a1` と同じ問い） |
| 昇降機を上げたままの短い移動 | **盤前の低速並進は th の範囲外**（th-system `Spec.md` §1。`O-d3`「担当する可能性があるがまだ含めない」）。点と点のあいだ・連盤の移動はこれに当たるので、範囲に入れるかから決める。**th は昇降機の高さを知らない。**加減速 0.4 m/s² と S 字の加減速は昇降機を最低にした状態の実測で決めた値（`Spec-safety.md` §3。最低でもピッチが約 4° 振れた）で、障害物・非常停止・通信途絶による停止は鈍らせない。上げたまま走ったときの急停止の揺れ・転倒に耐える保証は th 側に無い。`FK-V5` に加え、**昇降機を上げたときの速度・加速度の上限と急停止への耐性**を決めないと th は引き受けられない。th が高さを受け取って上限を切り替えるなら新しい連動になる |
| SLAM | §1 のとおり |

本システムが見落としていそうなもの（th の指摘）:
- §6 の自動迂回の不採用（いちばん大きい）と、SD-8・意図しない発進。
- 試験場内は速度上限 `v_slow`。
- th の「到着」は**向き合わせまで含む**（`Spec-onsite.md` §2.1.1）。定義を合わせる。
- 地図の凍結（§4.0.2）と、自己位置推定が立ち上がり直したときの扱い（§4.0.3）。
- 走行中に人がジョグすると一時停止になり、再開には人が「走行」を押す（`SM-3.1.1-14` ほか）。本システムが再開を指示できるかも SD-8 の話。
- 人物追跡: 盤前移動は不要、呼び寄せは必要。本システムの自律が盤前移動と同じ扱いなら不要で済む。

## 4. 本システムの実装管理担当からの指示を `CLAUDE.md` に入れるか

**入れてよい。ただし「指示」ではなく「依頼・申し送り」として受ける形がよい**（th の私見）。
th-system の `CLAUDE.md` は「ユーザーから方針変更の指示があったら、コードより先に spec を直す」なので、本システムからの申し送りはユーザーの指示ではない。
**受けたら th のユーザーに上げ、承認を得てから spec、コードの順**に進める。今回のような照会にはそのまま答えてよい。
申し送りの受付簿を th-system の `Spec-open.md` に「関連システム」節として置くと、本システムの [Spec-open.md](spec/Spec-open.md) §1.2 と対になる。

- ユーザーの判断: 要る（入れるか、どこに置くか）。
